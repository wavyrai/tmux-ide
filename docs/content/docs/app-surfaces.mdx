## Home

Home shows agents across your configured local and SSH machines. Each agent row
includes its machine, tmux server and session so identical session names stay
distinguishable. Select an available agent to open its terminal on that machine.

Use the machine filter to narrow the roster, or show only agents needing attention.
Connection and observation status remain visible: disconnected machines show
last-observed information, and their agents cannot be opened until the connection
recovers. One unavailable machine does not prevent other machines from updating.

The machine sidebar lists sessions and connection status. Home also provides
terminal, command and theme actions. When no tmux server exists, the terminal
browser offers a new-session action.

### Learn tmux-ide

Choose **Learn tmux-ide** on Home to start a guided walkthrough. It introduces
machines, servers, sessions, windows and panes, then guides you through splitting,
focusing and resizing panes, finding commands, changing themes and returning to
a running session.

Practice happens in a dedicated local tutorial session. Steps advance from
observed application changes, and progress is saved locally so you can pause and
resume. You can replay the walkthrough from Home. Your other sessions keep
running; the walkthrough does not close them.

Recent pane activity shows the latest reported reads and input actions, with
brief matching indicators in pane headers. This includes tmux-ide actions and
`send-keys`/`capture-pane` commands observed by the daemon's hooks on tracked
panes. Other tmux servers, untracked panes, and commands that bypass those hooks
are outside this view. External commands are not automatically attributed to an
agent, and the feed does not show the contents of input or captured text.

## Terminals

Terminals is a visual client for the selected tmux session:

- the left sidebar lists the current session and detected agents;
- the window strip reflects real tmux windows and creates new ones;
- every pane has a title, state, and relevant controls;
- terminal content is mirrored as terminal cells, including indexed and
  truecolor output;
- pane clicks and agent rows navigate to the canonical tmux pane;
- splitting, resizing, renaming, creation, and closing are daemon-owned tmux
  mutations, not a parallel layout model.

The UI retains terminal content through quiet periods, resize, theme switching,
daemon replacement, and viewer reattachment. tmux remains the source of truth.

### Scrolling

The mouse wheel acts on the pane under the pointer. At live output, applications
that request mouse input receive ordinary wheel events; otherwise, the wheel
scrolls terminal history locally. Hold Shift while scrolling to explicitly read
terminal history, including inside a mouse-enabled application.

While reading history or selecting text, scrolling stays local. Returning to the
bottom during a continuous history gesture does not send its remaining events to
the application. Press Escape to return to live output. Alt/Option+wheel remains
available for application scrolling at live output; Shift takes precedence.
Clicks and drags continue to follow the application's mouse mode.

### Selection and links

Drag to select and copy terminal text. Double-click selects a word; triple-click
selects a logical line, including its wrapped rows. Continue dragging while
scrolling, or hold the pointer above or below the pane to extend into history.
Escape clears selection and returns to live output. In a mouse-enabled
application, hold Shift to select locally, or use the pane's Select text action.

Local macOS copying uses the system clipboard and shows confirmation when the
write finishes. Over SSH and on other platforms, copying uses the host terminal's
OSC 52 support. To explicitly use that terminal route on macOS, launch with
`TMUX_IDE_CLIPBOARD_BACKEND=osc52 tmux-ide`. Terminal-routed confirmation indicates
that the request was sent; the terminal controls whether it is accepted.

Ctrl+click a visible HTTP or HTTPS URL to open it in your browser. Ordinary
clicks retain their existing terminal behavior. Links split across soft-wrapped
rows are recognized; this does not open links merely because a program prints them.

## Connect to another machine over SSH

Install the same tmux-ide beta build on both machines. The remote machine needs
Node.js and tmux, and `tmux-ide` must be available on the PATH used by noninteractive
SSH commands. Configure an SSH alias, key authentication, and host trust first:
the app uses `BatchMode=yes`, so it cannot prompt for a password or accept an
unknown host key.

Global installation upgrades an older running daemon on that machine. Its tmux
sessions keep running while TUI clients reconnect. A fresh install does not start
a daemon. If lifecycle scripts were skipped, app and headless launch also check
for an older daemon; you can explicitly run `tmux-ide update --daemon` to upgrade
it. An older CLI never replaces a newer daemon.

On the remote machine, start the daemon:

```bash
tmux-ide --headless
```

This runs in the foreground; keep that process alive in a separate shell. For a
managed service, use the [explicit supervisor setup](#supervised-daemon-upgrades).

If a healthy daemon already exists, the command reports
it and exits. Create any sessions you want to open using ordinary tmux on that
machine.

On your local machine, open the remote session browser or a named session:

```bash
tmux-ide app --ssh my-server
tmux-ide app --ssh my-server work
tmux-ide app --ssh my-server --ssh my-laptop
```

`my-server` can be an alias from `~/.ssh/config` or `user@host`. The app opens an
SSH tunnel to the existing remote daemon; it does not install software or start
a daemon remotely. Home and Terminals show the same machine sidebar and selected host label. Repeat
`--ssh` to include several machines alongside Local. Opening a session switches
the active terminal workspace to its machine; matching session names on different
machines remain separate. If you also provide a session name, it opens on the
first `--ssh` target.

Click **Add machine**, or press Ctrl+G to focus the machine sidebar and then A,
to connect another SSH target during this run. Enter an alias or `user@host` and
choose Connect. These additions are not saved to a configuration file.

With the sidebar focused, use Up/Down to move, Enter to open a session, and
Left/Right to collapse or expand a machine. The active session remains visible
when its group is collapsed. Escape returns focus to the workspace. Offline
cached sessions are marked unavailable and cannot be opened until reconnected.

If the connection drops, the app reconnects to that same host. It never silently
switches to your local daemon. Remote sessions and their processes remain owned
by tmux when you close the viewer. Creating a session or provisioning an agent
from the remote Home screen is not available in this beta; create those remotely
before opening them in the app.

On Linux, system tmux can serve the connection and normal terminal streaming.
Without the optional patched tmux build, retained history uses compatible
semantic reflow rather than native physical-grid backing. Older tmux versions
also expose fewer terminal-mode details, so this is not a claim of identical
behavior to the qualified native setup. Installing a different tmux executable
does not upgrade an already-running tmux server.

The TUI still runs locally with `app --ssh`, so local macOS clipboard copying
continues to use the system clipboard. Running the TUI itself inside an SSH shell
uses the terminal clipboard route described above.

## Commands and notifications

`F5` or `Ctrl+P` opens the command surface. Transient action notes, such as a successful
split, dismiss automatically and do not become permanent chrome.

## Project-defined views

WorkspaceConfigV1 can order full-panel views for `home`, `terminals`, `files`,
`diff`, and `missions`, or compose them with split and tab layouts. Files,
changes, dialogs, settings, palettes, and rich previews are loaded as optional
features so the resident terminal path stays small.

The Missions panel is presentational in this beta. `harnesses`, `agents`, and
`missions` workspace blocks are validated, but there is no public CLI command
that dispatches those mission defaults yet. `tmux-ide web` is also explicitly
unavailable; the daemon remains renderer-neutral for future clients.

## Supervised daemon upgrades

For automatic upgrades under a supervisor, explicitly reserve
its daemon namespace before the first service start:

```bash
tmux-ide daemon reserve-supervisor my-service --json
# Configure the service's foreground command:
tmux-ide --headless --supervised my-service
```

Run both commands with the same user and daemon state directory. The ID declares
ownership of that namespace; it does not install or identify an operating-system
service. Use `KeepAlive=true` with launchd or `Restart=always` with systemd:
upgrades exit successfully, so restart-on-failure alone is insufficient. The
service's stable executable/entry must already point to the updated installed
code before `tmux-ide update --daemon --if-running` requests replacement. The
updater waits for the supervisor and never starts a detached replacement for a
reserved namespace. An unavailable supervisor produces a bounded failure and
leaves the reservation intact.

Remove or disable the service and confirm its processes have stopped before
releasing the namespace:

```bash
tmux-ide daemon release-supervisor my-service --yes --json
```

Release refuses live or uncertain owners. It does not verify that the operating-system service was removed; that is an operator precondition. Existing unmarked services require a
one-time migration: stop and remove/disable the old service, reserve the stopped
namespace, then configure and start the supervised command. There is no implicit
migration or supervisor detection from process ancestry. Plain `--headless`
remains a foreground process and does not provide this automatic-upgrade contract.
Retained PID reuse after a cold boot remains conservatively refused pending
separate qualification. For systemd, also choose a process-group policy that
preserves external tmux sessions; this does not promise survival for tmux
processes placed inside a service cgroup that systemd kills.
